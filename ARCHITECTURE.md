# Outdoor Hounds MVP Architecture

Outdoor Hounds is an AI-guided service for Jenna Petersen's pet sitting business. It allows Jenna to manage her business profile and listings, and allows customers to browse adoptable pets, book group hikes, and arrange pet walks or sitting.

The system enforces strict human-in-the-loop guardrails. The AI assistant can propose setup changes and draft responses, but cannot publish changes, promise stock, or confirm bookings without explicit owner approval.

## High-Level Components

1.  **Frontend**: React + Vite (Single Page Application).
2.  **Backend**: FastAPI (Python 3.11+).
3.  **Database**: SQLite for local MVP and single-node deployment (swappable to PostgreSQL via SQLAlchemy).
4.  **LLM Layer**: Abstracted interface supporting a real provider (e.g., OpenAI/Gemini) and a local mock provider for free, deterministic testing.
5.  **Infra**: Dockerized containers deployed to a single GKE node via Kubernetes manifests.

## Data Model (SQLAlchemy)

*   `User`: Represents an owner or customer.
*   `BusinessProfile`: Jenna's business details, generated by AI and approved by Jenna.
*   `CatalogueItem`: Polymorphic item representing an adoptable pet, a group hike, or a pet walking/sitting service. Includes an `image_url` field.
*   `Enquiry`: A customer request (adoption application, hike booking request).
*   `AssistantRule`: Approved rules governing what the customer-facing AI can say.
*   `AuditEvent`: Immutable log of AI decisions, human approvals, and critical state changes.

## Backend Layered Architecture

*   **`app/models/`**: SQLAlchemy ORM models defining the database schema.
*   **`app/schemas/`**: Pydantic models for API request/response validation.
*   **`app/repositories/`**: Data access layer isolating database queries from business logic.
*   **`app/services/`**: Core business logic, including the setup workflow and enquiry processing.
*   **`app/llm/`**: The LLM abstraction. Contains the `LLMProvider` interface, `RealLLMProvider`, `MockLLMProvider` (fixtures), and an `LLMFactory`.
*   **`app/policy/`**: Guardrail logic enforcing human approval thresholds and scam/safety checks.
*   **`app/routes/`**: FastAPI endpoints. These remain thin, delegating to services.

## Guardrail Pattern

The system implements the "Agentic Workflow Guardrails" pattern:

1.  **Clear Actions**: The AI can only take specific actions defined in its tools (e.g., `propose_listing`, `draft_response`).
2.  **Approval Gate**: State changes (e.g., publishing a listing, confirming a booking) enter a `pending_review` state.
3.  **Audit Trail**: Every AI proposal and human approval is logged in the `AuditEvent` table, linking the action to the user and the specific AI trace.

## Deployment (Single Node GKE)

The application is packaged into Docker containers (Frontend Nginx, Backend Uvicorn). The infrastructure configuration provides Kubernetes manifests (`deployment.yaml`, `service.yaml`, `ingress.yaml`) configured for a single-node GKE cluster (e.g., `e2-small` or `e2-medium`), avoiding complex distributed state for the MVP. Local media is mounted via a persistent volume claim or served directly from the container for the MVP.
